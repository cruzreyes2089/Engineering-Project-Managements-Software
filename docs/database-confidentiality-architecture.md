# Single-user database confidentiality architecture — candidate

## Decision proposed for owner/security review

Keep current standard SQLite provider for initial internal-only single-user scope; no encryption dependency change or conversion of existing database. Microsoft's SQLite documentation confirms standard SQLite is not encrypted and Password connection-string keyword has no effect without supporting native provider. Do not advertise this as an encrypted database. Reference: https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/encryption and https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/connection-strings .

Require independently verified Windows fixed-volume encryption (BitLocker/device encryption or reviewed equivalent), private dedicated Windows account, restrictive NTFS ACLs for program data, current security updates and separately protected backup storage. BitLocker protects offline volumes; it does not prevent a same-user process, administrator or already unlocked volume from reading data. Recovery passwords/keys must be stored securely apart from the device, with authorized recovery drill on a separate system. Never commit or log keys or upload company databases to public services. References: https://learn.microsoft.com/windows/security/information-protection/bitlocker/bitlocker-overview and https://learn.microsoft.com/en-us/windows/security/operating-system-security/data-protection/bitlocker/recovery-overview .

## Implemented candidate control

New desktop-created development and acceptance workspace directories are created with protected explicit Windows ACLs granting current Windows SID, SYSTEM and local Administrators full control, inheritable by child files/directories. Validate owner, canonical non-null DACL and exact expected rule layout after creation. No automatic rewriting of existing workspace directories, existing files, user profile, or ACLs. A new directory created concurrently may be rejected if its ACL differs. The helper exposes a conservative read-only directory layout assessment; false does not establish that a directory is public or unsafe, merely that exact policy was not demonstrated. Non-Windows path creation remains synthetic-development only, never a qualified production ACL. No SID values are logged. Reference: https://learn.microsoft.com/en-us/dotnet/api/system.io.filesystemaclextensions.create?view=net-10.0 .

This is a concrete creation-time restriction, not an effective-access audit of ancestors/descendants, protection against ACL mutation, inherited delete rights, administrators or same-user malware. Existing workspace ACLs are not automatically qualified; SQLite files and recovery destinations require independent validation. No production path or automatic migration enabled.

## Backup and key recovery

Recovery copies contain confidential client, project, document, credential-hash and financial evidence even after removing Manager API profiles. Current .db recovery files are plaintext SQLite; hash integrity is not confidentiality. Save only to separately approved encrypted storage with limited ACL, verified encryption status, separate retained SHA-256, access-controlled retention, and tested recovery on a clean isolated device. Keep source and recovery copies separate; never silently overwrite, promote or downgrade. DPAPI CurrentUser protects stored Manager credentials only; recovery copies deliberately exclude them. Re-enroll with new credentials after an approved restore, never infer financial authority. No automatic BitLocker enable/disable, recovery-key read or backup migration is implemented. No user settings changed by source work.

## Before production

Independent reviewer must qualify actual data volume encryption, dedicated account/ACL (including existing files, sidecars, recovery staging and backup destinations), device loss/recovery, unencrypted export handling, recovery key custody and rotation, clean restore, endpoint security and signed installer. If application-level encryption is required, evaluate supported SQLCipher or equivalent native provider, dependency licensing/provenance, key derivation/storage/rotation, encrypted journal/temp/backup behavior, loss of Windows profile, cross-device restore, old SQLite migration and complete native/desktop regression. Never simulate encryption by storing a password or inventing a custom cipher. The current prototype cannot be represented as whole-database encryption. No authorization for real records, distribution or security-hold change.

Windows regression required for new ACL code; native tests check newly created directory policy, inherited marker principals, no existing ACL rewrite, and an unexpected broad grant. No actual user's filesystem was inspected or modified.

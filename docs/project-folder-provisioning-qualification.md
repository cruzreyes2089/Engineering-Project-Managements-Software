# Synthetic physical folder provisioning qualification

The current application remains preview-only, schema 47, with no physical folder command or storage registration. Revision CRC-Production-2 has nine flat production folders, optional correspondence, no automatic or optional MEP subdirectories, and a separate logical restricted administration boundary.

The ordinary native smoke suite now exercises a physical provisioning candidate in an owned, disposable synthetic workspace. The candidate derives all entries from the current fixed template and project identity, checks root ancestors and target directories for reparse points and non-directory collisions, and binds the exact logical plan, separate synthetic roots and observed existing/missing state into a review fingerprint. A new review is necessary after any selection or observed state change. Explicit confirmation is required. It creates missing directories only, never overwrites or removes files, never moves records and verifies the resulting directory state. An interruption is treated as incomplete, not rolled back by deleting folders; a fresh review can safely repair missing directories in the fixture. The smoke suite checks stale reviews, wrong-project replay, existing files, collision rejection, interrupted creation, idempotent replay, optional correspondence, separate roots and absence of MEP children. Real symlink denial is checked only if the environment permits creating a synthetic symlink; otherwise it is explicitly reported as unqualified.

The candidate is test-only, not a production path-validation or access-control solution. The test roots are created by the harness; they are not registered firm storage. The path checks cannot exclude hostile concurrent filesystem replacements, aliases/hard links or all Windows namespace edge cases; separate synthetic directories do not prove OS ACL separation. No credentials, actual firm storage, external folder adoption, network/share support, ACL configuration, application-level commit/audit journal, or release authorization. Before production integration, qualify Windows handle-based/no-follow filesystem operations or an appropriately protected exclusive storage boundary, validate actual ACLs and root identity, record reviewed template and durable attempt/outcome evidence, and verify recoverability after interrupted operations. Existing directories in real storage must not be adopted by this synthetic fixture behavior. Source tests pending exact-revision Windows CI.

## Durable synthetic operation journal

A separate SQLite journal in the test-owned workspace now commits an immutable intent before any folder creation and an immutable outcome only after verified completion. Missing outcome is Uncertain, never success; restart cannot silently retry. A fresh observed review, explicit confirmation and matching project/plan are required to supersede an uncertain attempt and create its linked repair. No rollback deletes physical directories. A lost acknowledgement after successful creation is reconciled by a zero-create repair, retaining both attempts. The synthetic test checks reopened uncertainty, stale/changed/wrong-project recovery refusal, interruption, lost acknowledgement and immutable evidence. SQLite synchronous FULL and a serialized transaction protect journal changes; no claim of atomicity between SQLite and the filesystem. This is a single-process synthetic candidate, not a production concurrency lock or authenticated audit log. Before activation qualify interprocess fencing, root/handle identity, ACLs, storage registration and recovery backup pairing. Native schema 47 and application preview-only behavior are unchanged. Exact-revision regression is pending.

## Cooperative cross-process fencing

The synthetic journal now holds an exclusive file handle on an existing, empty lock file in its owned workspace from review revalidation through durable intent, physical execution and confirmed outcome. All participating operations on that workspace serialize, including different projects. The handle is released on exception; an uncertain durable record is not silently cleared. The smoke executable has a read-only subprocess probe of the existing synthetic lock, with no directory creation or journal write path; tests verify held/free behavior and attempt to supersede a still-running operation. A final observation immediately before confirmation rejects missing directories, and repair retains both attempts. The project ID and journal parent are checked against the synthetic provisioner's identity. This is cooperative locking, not an OS permission boundary or a guarantee against hostile filesystem mutation. The lock file must not be removed/replaced; real Windows identity and ACL qualification, crash/backup pairing and production storage activation remain open. No application schema changes or real file operations. Pending exact-revision CI.

## Actual synthetic process termination

The smoke suite now launches a separate fixed-scenario worker in a random, newly created temporary workspace. It accepts no filesystem path or live data. The parent terminates that specific child during partial directory creation and after all directories exist but before durable acknowledgement. It verifies the OS fence was held and is released by termination, the durable attempt is uncertain after reopening, physical progress is preserved, blind replay is refused, and explicit linked repair completes the flat production tree. No live storage or database is involved. This qualifies process termination rather than power loss, OS crash, filesystem durability or real ACL boundaries. ## Windows directory identity candidate

The test-only Windows adapter opens directory handles with FILE_FLAG_BACKUP_SEMANTICS and FILE_FLAG_OPEN_REPARSE_POINT, verifies the actual handle describes a non-reparse directory, and reads volume serial and file index. The reviewed fingerprint binds existing directory identities and the workspace/production/restricted root identities, in addition to the logical plan and presence observations. During synthetic Apply, workspace and root handles plus each current parent handle omit delete sharing, and already-present directory identities are rechecked. Tests exercise handle identity retention across rename and same-path directory replacement invalidating a review. A metadata handle does not guarantee rename exclusion. Other platforms retain existence-only qualification and explicitly report Windows identity checks unqualified. This is not a handle-relative filesystem implementation: intermediate path resolution, malicious concurrent replacements, volume serial/file index lifetime and actual ACLs remain separate security issues. The adapter is confined to smoke tests; no physical operations exposed in the application, no new schema and no release approval. Exact-revision CI pending.

## Windows synthetic ACL descriptor qualification

A separate Windows-only smoke fixture applies a protected, explicit owner/SYSTEM full-control ACL to two new empty synthetic storage roots. It reads raw descriptors and rejects null/non-present DACLs, wrong root owner, unexpected inheritance protection, extra or missing principals, deny/callback/nonstandard ACEs, rights and inheritance flag mismatch. Every existing planned descendant must have the expected inherited-only ACL. Root and descendant descriptor digests are paired with the directory-identity review. Tests introduce and remove a broad Everyone read grant, explicit child grant and protected child ACL; both roots and child permissions are modified only within the disposable fixture. The review itself is nonmutating; this is a strict synthetic single-owner descriptor policy, not a production policy for engineering staff, an effective-access test under a separate Windows token, or proof of isolation from administrators. No real Windows accounts, groups, directory permissions or production storage configuration are changed. The underlying candidate remains test-only; final security policy must support actual firm roles and independent effective-access qualification, and must enforce the ACL review in its durable operation boundary. No schema change. Exact-revision CI pending.

# Code signing policy — proposed, not operational

CRC Practice Manager is an Apache-2.0 free public-use project. No signing provider, certificate, project-specific publisher profile, production release key or signing permission has been approved or provisioned. The original blocked v0.4.12 archive remains excluded. No unsigned executable release is authorized.

## Provider decision

Evaluate [SignPath Foundation](https://signpath.org/terms) first for zero-cost OSS signing. The provider requires an existing release in the intended form, ongoing maintenance, eligible components/licenses, verifiable build provenance, documented functionality, MFA, designated reviewers and human approval of signing. Its certificate names the Foundation; a project-specific signed release binding is essential and a shared publisher name alone is insufficient. The existing release hold means eligibility cannot be assumed. Ask the provider about the held pre-release situation before an application; never distribute an unqualified binary to satisfy eligibility. No application has been submitted. No provider attribution implying acceptance is authorized.

Alternative: [Microsoft Artifact Signing](https://learn.microsoft.com/azure/artifact-signing/concept-certificate-management), Public Trust only, subject to identity validation, cost approval and positive compatibility testing. Daily-renewed short-lived certificates require durable profile-specific identity validation and a timestamped signing design; current leaf-pin-only implementation cannot establish rotation readiness. No private test certificate, trust-root installation, user security exception or signing bypass for official releases.

## Trust and custody design

- Require Windows native trusted Authenticode verification, appropriate code signing EKU, timestamp validation and revocation evidence, exact final SHA-256, and independently provisioned project release authorization. Never accept a publisher string, a CA name, an arbitrary certificate contained in a package, or a package-supplied key alone as authorization.
- Retain exact leaf pins for current held implementation. A later reviewed signed release manifest may bind the precise certificate identities of each artifact (including multiple independently verified leaf certificates) to exact artifact hashes and an independently established project release trust anchor. If a durable provider-specific profile is chosen, validate the full profile identifier, appropriate trust chain and code signing purpose. Reject unknown/retired/revoked identities; protect root rotation and monotonic release decisions from rollback. No automatic trust-on-first-use. Do not replace existing leaf checks until positive and negative real-Windows acceptance succeeds. Current cached-only revocation and lifetime signing flags need explicit review for expired but valid timestamped signatures. A signature alone cannot authorize execution.
- Use a protected release approval environment, MFA, least privilege, separate build and signing approvals, provider-protected non-exportable signing keys and auditable release requests. No keys or credentials in source, artifacts, command transcripts or public CI. Require independently retained project release metadata signing-key custody and recovery procedure, not the same key as the executable signing provider. No self-hosted runner on the owner's everyday computer.
- Sign first-party desktop/coordinator/uninstaller before generating the final payload inventory and signing the outer package; preserve upstream signatures and license notices. Final signed package inventory and independent detached authorization avoid circular hashes. Validate every artifact and exact metadata; sign outer package last. No post-signing mutation. Exact signed hashes, Defender scan with active protection and current definitions, signature chain, timestamp and project binding must qualify before isolated execution. All gate requirements remain in force.
- Confirm author/reviewer/approver roles, actual MFA configuration and private reporting channel before signing service onboarding. Owner approval is necessary; this document does not certify identities or controls. Final public release requires separate explicit approval after all mandatory gates, even if the provider permits signing.

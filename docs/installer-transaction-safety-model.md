# Installation transaction safety model (synthetic only)

The versioned installer proposal is still subject to independent security and owner review. No install engine, pointer writer, filesystem lock, journal writer, production startup or uninstall engine is delivered by this change. The model is deliberately pure, takes synthetic observations, and never authorizes release, execution, automated rollback or data removal.

Transaction design:
- Exact prior and candidate commit, payload hash and schema; existing database hash, isolated recovery hash and rehearsal bindings. Fresh install cannot adopt existing data. Downgrade refused. Backup evidence means an independently verified recovery copy in a future implementation, not merely a provided string.
- Durable phases Planned, Staged, SwitchIntent, Activated, Accepted. Stage complete immutable version, verify all bytes, flush file and directory evidence, acquire exclusive local installation/application lock, check original data and recovery evidence again, persist intent before atomic same-volume active-pointer replacement. Record and verify actual pointer result before activation. No staging changes to database.
- Interruption before intent: stage again only if the active version and original source evidence are unchanged; unexpected pointer, staged payload or missing recovery stops. After intent, exact old pointer plus unchanged source permits reviewed switch; exact new pointer plus unchanged source permits reviewing observed result. Ambiguous pointers or changed data before durable activation hold. Never infer that the previous binary may be relaunched or revert a new-schema database automatically, even on same-schema upgrade. After activation, require verified application acceptance and correct schema before acceptance; the model does not prove logical database preservation or authenticity.
- Uninstall: code-only removal review requires a closed application, exclusive lock and verified installed identity. Preserve database, all data directories, recovery evidence, logs and unknown files. No recursive delete of a user-supplied or shared directory; actual implementation must use exact reviewed paths and independent post-uninstall witness.
- Physical implementation qualification remains outstanding: filesystem atomicity and durable journal behavior on Windows NTFS, real competing processes, reparse/hardlink checks, filesystem ACLs, disk-full, interruption at every durable transition, clean VM, exact signed package, and backup restore/recovery procedures. A journal or claimed observation alone cannot prove safety. The model makes no filesystem calls and must not be treated as actual installer qualification.

Eight regression methods exercise the state model, invalid inputs, crash-boundary observations, missing staging, recovery mismatch, stale source, downgrade, fresh-install protection and uninstall policy. Windows CI required on the new revision. No security hold change, distribution, production data or executable installer.

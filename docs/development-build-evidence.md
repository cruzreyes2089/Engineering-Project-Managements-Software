# Development build evidence and release gate

The Windows CI job now records the complete relative-path/byte-count/SHA-256 manifest for the quarantined self-contained publish output, with a digest of its compact UTF-8 JSON. It verifies the expected entry point and managed runtime files, rejects unexpected paths/reparse points and caps inventory size. The manifest contains only CI-generated file metadata, not user records or absolute paths. No artifact upload. Dependency report checks require the correct project identity, inventory framework scope, transitive-package identity and the expected advisory source. A vulnerability report with no frameworks can be a legitimate clean response in the observed SDK; this is not treated as a missing inventory because the separate inventory report must contain frameworks. No claim that NuGet advisories detect malicious packages or that file hashes establish safety.

Before release, separately obtain independent security review of the intended exact release, complete desktop acceptance on a trusted machine, verify the signed package, publisher and installer/update/uninstall data retention, restore/reconciliation qualification, and explicit authorization to release. The previous Chrome warning and original blocked artifact are investigation evidence, not a release candidate. No signing secrets are created or committed, no browser protection changes, and no automatic distribution. CI remains source-only and publishes to an ephemeral runner directory for inspection. The file manifest is not an authenticated provenance attestation or a proof of reproducible builds; a subsequent independent review must verify that the tested and delivered bytes are the same.

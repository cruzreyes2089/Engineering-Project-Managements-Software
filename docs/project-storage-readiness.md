# Saved storage location inspection — development

The project Storage assignment dialog now offers an explicitly confirmed read-only metadata inspection of the exact current saved inactive assignment. The service validates role, restricted/document/project/client access and expected binding revision before reading and rechecks access and binding afterward. It does not persist observations, enumerate folders, read document contents, write files, create directories or change the database. The initial candidate supports Windows fixed NTFS drives only; no UNC, cloud or mapped storage qualification is claimed. It opens each ancestor and planned directory using a metadata-only handle with final-component reparse-point refusal, checks directory identity, detects identical or nested root identities, rejects redirected and obstructed components, skips descendants of missing/blocked parents, and reobserves root identities after the walk. Existing project directories are flagged for separate adoption review, not accepted automatically. The result includes counts and a point-in-time fingerprint; no path or identity logging.

This is not a secure handle-relative filesystem mutation mechanism or effective ACL test. Metadata opens may allow rename and ancestor resolution is still path-based; a hostile concurrent change can invalidate the observation. No result sets FilesystemVerified, EffectiveAccessQualified or ProvisioningAuthorized. The Windows-only synthetic smoke fixture exercises missing roots, empty project paths, collisions, reparse refusal when supported, stale assignments and access denial. No actual business storage was accessed in development. Database schema 54 unchanged. Exact-revision regression pending.

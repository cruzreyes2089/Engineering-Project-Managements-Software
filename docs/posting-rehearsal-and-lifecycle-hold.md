# Durable posting rehearsal and lifecycle hold (schema 7)

Build #37 verified 15 Python + 361 C# checks, zero compiler warnings/errors, zero uploaded artifacts.

This milestone introduces only an offline synthetic intent journal, not an authorized posting workflow. No HTTP POST/PUT/PATCH/DELETE route exists. Intent source keys are unique across all users and revisions in one database; the future approved draft must persist its original key. The versioned canonical fingerprint binds kind, customer, account, allocation, amount, date and explicit currency. USD in tests is synthetic only; prior null API currency has not established USD. The journal stores a hash, not full payload, and never returns attempt keys on repeat reserve/read. A single immediate SQLite transaction wins each reserve/begin. A started intent is conservatively uncertain if the process crashes; no lease expiry or automatic retry. Only never-started intents can cancel, with permanent source-key consumption. Uncertain or inflight history blocks any new begin. Simulated external IDs are globally unique and clearly segregated from real mappings. There is no uncertain resolution method until independent provider evidence is designed. Rehearsal state has no network side effects. Role grants are separate and revoked permissions remain revoked.

An explicit, sticky local hold for a declared clone, restore or suspected identity change blocks new rehearsal operations; inspection remains possible to authorized users. No automatic reset. It does NOT detect an exact clone, undo restored database history, or prove a live business identity. A copy/restore of both CRC and Manager can roll back local evidence. Before any future write integration: separate test/live systems, independent identity verification, recovery reconciliation against authoritative provider, rotate clone marker/token, durable external evidence that survives restore, manual review of all uncertain transactions and independently approved posting permission. Keep production and posting disabled until those requirements and actual documented write behavior are verified. No new binary distribution. Old v6 binaries cannot open v7; back up the closed development database before eventual authorized testing. No operational invoice/payment module or provider write connector is yet implemented.

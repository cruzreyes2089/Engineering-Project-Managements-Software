# Observed API2 synthetic form validation (source-only)

The owner's independent GET diagnostic returned all five forms with HTTP 200. It established field paths and types, not values. This validator compares expected UUIDs from a trusted future acquisition layer against both Key and id and the observed line/account/allocation fields. Exact one-line test amounts, no tax/project flags, account code/name and P&L flag are deliberate synthetic constraints. A bank/cash account record UUID is distinct from the cash control account UUID; ReceivingBankAccount must come from the receipt list's receivedIn.key and be independently confirmed, never the cash control account. The diagnostic must verify all actual equalities and flags before the adapter contract is accepted.

PartialMatch explicitly does not establish the invoice's missing customer UUID, the group classification, ledger completeness, dates, or a production posting contract. Key/id equivalence and flag values are hypotheses that must be checked on the live fixture. No adapter/UI wiring, no credentials, no writes, no executable upload. Do not treat a failing synthetic assumption as a Manager bug or broaden automatically. The original blocked artifact hold remains in effect. Use existing read-only PowerShell diagnostic for live comparisons; no actual keys in reports.

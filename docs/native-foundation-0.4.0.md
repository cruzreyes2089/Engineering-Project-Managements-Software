# CRC Practice Manager — native foundation 0.4.0
**Development source, not a production or commercial release.**

This slice implements the initial local firm setup, sign-in/logout, scoped permission checks, client and contact create/edit/search and a preliminary dashboard in C#/WPF with SQLite. No Microsoft Access or Office dependency at runtime. All other Access features remain in the migration register, not implemented. Use synthetic data only. First-run uses a separate local development database under `%LOCALAPPDATA%\CRC Practice Manager DEV\practice-dev.db`. No legacy records imported or modified. No default login; create your own 14–256 character development password. There is currently no password reset UI or user/role management UI; do not depend on this build for real work.

## Build (Windows)
Prefer CI: run the Windows development build workflow in this repository. It restores dependencies, compiles, runs schema and C# smoke checks, publishes a self-contained Windows x64 development executable artifact only on success. Review the workflow results for the exact commit before using its artifact.

Local alternative: install the .NET 10 **SDK** from https://dotnet.microsoft.com/download/dotnet/10.0, extract this ZIP, then run `BUILD_DEVELOPMENT.cmd`. This executes the build/test/publish script once and keeps the console open. If it succeeds, open `artifacts\win-x64\CRC.PracticeManager.exe` from the entire published folder. No MSI/installer yet. Do not move only the exe (dependencies required). If there is an error, send the error output. Do not modify Access. You can also use PowerShell `./BUILD_AND_TEST.ps1 -Publish`. Use a local path, not a network SQLite share.

## Design choices (author proposals)
- Local single-firm development mode only. A firm-local role and four explicit CRM permissions are seeded at setup, not the real Access role grants. No administrator bypass. Denied permissions rechecked in services. No password reset flow, forced change UI, other roles UI, per-project access or server isolation yet. Persisted failed-attempt lockout for known accounts; session is limited to eight hours and rechecked on service calls; UI idle lock and timing equalization remain pending. OS owner can access the SQLite file directly; this is not a security boundary against that user.
- Direct Microsoft.Data.Sqlite SQL service for this limited slice (rather than EF Core proposed in M03); evaluate ORM/provider strategy before expansion. Versioned schema 1 rejects unknown versions; no upgrade migration needed yet. No shared network SQLite. PostgreSQL and API later.
- Client type/status values retained from the legacy application; sequential `CL-000001` default format, primary-contact uniqueness/replacement, inactive-client contact guard and max notes length are proposed development defaults (legacy numbering uses numeric or C-0000 formats; preserved identifiers and exact migration policy are pending). Reconcile exact Access seeds/numbering/status semantics before migration. Existing Access fields preserved in models where possible. No deletion functionality. Search uses SQLite ASCII case folding; international search and paging pending. View is not safe against direct OS file reads. No billing or accounting engine yet.
- Native WPF UI currently uses code-behind as a thin service adapter, not full MVVM. Planned modules shown as informational text. No claim of full UX parity.

See the public requirements and acceptance registers in docs. Full internal Access traceability remains in the original local archive. Do not upload confidential Access files or source exports to GitHub. No licenses or signing secrets are included.

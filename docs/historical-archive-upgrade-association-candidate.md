# Historical archive upgrade and association review — schema 47 candidate

Candidate branch only. No schema change beyond 47, no promotion of the schema 46 branch, no release or security-hold change.

Upgrade rehearsal now uses an internal deterministic SHA-256 witness over the sealed historical batch metadata, review note, actor, seal, every archived field and mapped native client ID. Ordered JSON row encoding separates queries and records. Before and after snapshots must match both historical record count and fingerprint, in addition to the existing CRM/user/audit identity checks. Pre-47 sources and genuinely empty 47 archives use the same empty sentinel. Incomplete archives and inconsistent CRM mappings fail closed before any disposable upgrade is accepted. The digest is not exposed in the result, and the result reports archive count and preservation only. This is a same-rehearsal comparison, not a cryptographic signature or independent source authenticity guarantee.

A populated schema 47 recovery copy is now covered by a current-schema disposable reopen rehearsal. This does not prove an upgrade to a future schema version. A damaged clone with missing seal must be refused. Existing schema 1 upgrade rehearsal remains a separate test.

The new PreviewHistoricalAssociation method requires historical import administrator authority, archive/client access and native project view. It accepts an exact original archive identity and explicit existing native project ID. It validates the sealed archive and CRM mapping, requires the same native client identity, and verifies the accepted native proposal snapshot using the existing ProjectRow guard. The returned review binds the project transfer and native proposal digests and compares title/site exactly; absent site evidence is reported as unavailable, not a match. A text match is not proof of project identity. There is no write, audit mutation, automatic association, persistent link, project creation, agreement substitution, conflict clearance or work authorization. Future persisted associations require separate approval, immutable evidence, duplicate/reversal rules and regression tests; they may never affect operational authorization.

Native regressions specify populated rehearsal, incomplete clone rejection, exact historical identity and same-client checks, missing-site uncertainty, permission denial, unchanged audit and project state, and continued signed-agreement requirement. The association fixture creates a native proposal/project only through the ordinary workflow in the disposable restored database, not the original archive.

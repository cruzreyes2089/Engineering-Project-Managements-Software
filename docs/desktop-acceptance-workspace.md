# Desktop acceptance workspace — test-first specification

Separate opt-in synthetic workspace under LocalApplicationData, not a live database picker. No arguments preserves existing development path; --acceptance-new reserves a fresh UUID folder; --acceptance-session <32 lowercase hex UUID> opens only an existing initialized acceptance workspace with its exact marker. Reject unknown/malformed arguments without default fallback, never accept arbitrary file paths, check workspace reparse points, refuse missing/changed marker or database, and show acceptance ID in main title and status. No automatic deletion, no credentials or real data, no production accounting. This is protection against accidental workspace selection, not a security sandbox or malicious local administrator. Use a dedicated isolated Windows VM with network/real credentials unavailable for offline acceptance, only after security approval; do not run or distribute quarantined executable. Test-first stub deliberately fails; functional CI and interactive desktop acceptance distinct. No new database schema.

## Operating procedure (after independent security approval only)

Use a dedicated clean Windows VM or isolated Windows user profile, with real firm files, Manager credentials and production database unavailable. Disconnect networking for internal workflow tests. The source changes do not grant permission to run a held build.

1. Launch the qualified desktop executable with --acceptance-new (no other arguments). Confirm SYNTHETIC ACCEPTANCE and the exact session ID are visible in the window title and header. Bootstrap a synthetic firm, distinct test credentials and numbering prefix. Do not use actual credentials or clients.
2. Record the exact build commit, artifact SHA-256, Windows environment, session ID, test ID from legacy-acceptance-register.csv, reviewer, expected and observed result. Store test evidence privately.
3. Execute the core CRM, proposal, signed test-document and project authorization, party clearance, planning, attendance, work review, invoice preparation and reporting scenarios in the register. Use independent synthetic identities where required; never claim approval based on UI visibility alone.
4. Exit and reopen with --acceptance-session ID (the exact 32 lowercase hexadecimal session identifier shown in the title). Verify persistent synthetic records; test invalid ID, unknown option and missing marker rejection without default database fallback. Never provide a file path. Check the normal development store remains unchanged.
5. Run recovery and migration scenarios using separate synthetic copies and files, not production data. Test accounting only in its separately approved disposable fixture; no live accounting access or writes. The acceptance workspace does not enforce OS-level network isolation or prevent a user entering real data; the isolated environment and operator controls are required.

A new acceptance workspace reserves a unique folder and marker but the normal service initializes the database. Reopening requires a matching marker and existing regular database file, not necessarily a bootstrapped firm. Reparse checks cover acceptance root, session directory, marker and DB; the OS-provided local profile root is trusted. No arbitrary path selection, automatic cleanup or default fallback. Source regression checks do not execute actual WPF interaction or replace security approval.

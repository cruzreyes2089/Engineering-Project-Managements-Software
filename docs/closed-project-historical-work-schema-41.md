# Closed-project historical work — proposed schema 41

Base bc225db (verified schema 40). Ordinary new submissions remain blocked after operational closure. An explicit employee-owned historical actual-fact workflow allows omitted time and expense records without reopening a project or authorizing new work, including during current conflict holds.

- Current exact closure event ID, immutable local calendar cutoff, date inside original task plan and on/before cutoff and any discontinuation date. Physical project start evidence, own started/completed task (including discontinued, never cancelled), active employee, current Work.Own, existing daily cap and expense validations. Existing work-date policy does not prove actual date/time of performance; explicit attestation and review required. Calendar-day precision cannot establish intra-day sequence or prove that work fell outside a previous closed interval. Do not use this as authorization to work or evade conflict controls.
- Add closure-local-date evidence to lifecycle events: for new events record SQLite local date at decision; derive legacy event dates from recorded UTC in local machine timezone at migration, label inferred values, reject missing/unparseable values for historical path. Persist thereafter; do not recalculate on later timezone changes. Historical fact itself records closure ID and mandatory reason as immutable fields. Exact replay checks normalized content, closure, reason; ordinary submission cannot reuse historical operation and vice versa. No automatic project reopen or billing classification. Existing independent review/explicit founding-owner policy remains; no special self-approval bypass.
- Show own and manager historical evidence and pending review; retain existing reports and closeout state. No production posting or accounting changes. Separate linked correction path for rejected/invalidated historical facts and closed-project invalidation is deferred to the next slice; do not silently drop lineage. Historical entries remain subject to independent factual review, including potential rejection, even after closure.
- Test-first stub intentionally fails. Migration/restore, atomic audit, concurrent retry, direct SQL guards, desktop entry, full Windows regression before promotion. No main merge, production data, or distribution.

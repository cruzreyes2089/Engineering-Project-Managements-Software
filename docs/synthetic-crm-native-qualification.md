# Native synthetic CRM qualification

The native smoke suite now contains a fixed independent expected-value fixture for the two DAO-generated scenarios. Ordinary CI exercises handcrafted equivalents, not actual DAO output. An opt-in Windows qualification run can pass exact DAO-generated transfer bytes to the separately reviewed, already built Release smoke harness. No desktop build distribution, production import, or release authorization.

After independent approval to execute the exact source/build in an isolated environment, run the existing Windows source build and test procedure, then:

    python tools/migration/qualify_synthetic_crm.py --confirm-synthetic --dao-bitness 64 --native-smoke

Select 32 for a 32-bit DAO engine. The harness uses dotnet run --no-build --no-restore for the previously built smoke project; it does not itself establish build provenance. Independently verify the exact source revision and approved smoke binary before execution. No input database path is accepted by the Python harness. Native test mode accepts only bounded transfer bytes, an explicit fixed fixture mode, and the matching digest; native parsed records must match the two hard-coded synthetic fixtures before opening SQLite. No actual CRC records, private artifacts or credentials are intended. Temporary synthetic databases are isolated from the default application database. Cleanup or execution failures are not a pass.

Checks specified: unauthenticated preview and revoked-grant import denial; exact preview hash and explicit confirmation; forced failure during sequence update after row and mapping insertion; rollback of rows, mappings, batch, audit events and numbering; complete client and contact service projection equality against independent expected values; raw stored leading-zero postal and empty phone check; parent links, original IDs, native numbers, counts, exact repeat and changed-package rejection. The Python driver requires a successful native exit and matching transfer digest in the completion marker, and checks transfer and Access source bytes are unchanged. Normal CI does not run actual DAO. Native full field comparison is through service projections, with selected raw SQL assertions; it is not a general database reconciliation tool.
